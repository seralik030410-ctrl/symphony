# FinCtrl 3.0 — мультимодальный runtime

**Статус:** согласовано для планирования  
**Дата:** 2026-09-07  
**Основа:** `docs/SYMPHONY_2_REBUILD_SPEC.md` и существующая реализация FinCtrl 2.x

## 1. Цель

Добавить в FinCtrl полноценный голосовой режим, расширенный Vision и генерацию изображений/видео через ComfyUI, не ломая прямой текстовый чат, изоляцию sessions/turns, event store и существующие настройки моделей.

Система должна работать локально по умолчанию. Облачные OpenAI-compatible и специализированные API-провайдеры подключаются только по желанию пользователя. Отсутствие API-ключей или интернета не должно мешать локальному чату.

## 2. Выбранный подход

Рассматривались три варианта:

1. Одна Omni-модель для всего. Даёт хороший realtime, но привязывает продукт к конкретной модели и требует мощного оборудования.
2. Только модульная цепочка `STT → LLM/Vision → TTS`. Поддерживает больше моделей, но имеет большую задержку и не использует преимущества нативных speech-to-speech моделей.
3. Единая capability-архитектура с двумя голосовыми контурами и отдельным media runtime. Это выбранный вариант.

FinCtrl поддерживает одновременно:

- нативные Omni/realtime-модели;
- модульную цепочку распознавания, рассуждения и синтеза речи;
- локальные и API-профили каждого компонента;
- ComfyUI как независимый генеративный runtime;
- существующий прямой текстовый чат без обязательного document/media router.

## 3. Архитектурные границы

### 3.1 Provider Registry

Над существующим Model Gateway появляется общий реестр возможностей. Один профиль провайдера может объявлять:

- `text.chat`;
- `vision.images`;
- `vision.live_frames`;
- `audio.transcription`;
- `audio.synthesis`;
- `audio.realtime`;
- `media.image_generation`;
- `media.video_generation`.

Model Gateway продолжает отвечать только за LLM/Vision-вызовы. Голосовой realtime и долгие media-задачи не помещаются внутрь него, а получают собственные gateways. Это не позволяет одному медленному видео-заданию блокировать чат.

Профиль хранит URL, модель, таймауты, ограничения и ссылку на секрет. API-ключи не записываются открытым текстом в SQLite: desktop-версия использует системное хранилище секретов, серверная — переменные окружения или внешний secret store.

### 3.2 Voice Runtime

Voice Runtime имеет единый state machine:

`idle → listening → transcribing/thinking → speaking → idle`

Из любого активного состояния возможны `interrupted`, `cancelled` и `error`. UI отображает эти состояния, но технические события остаются сворачиваемыми и не засоряют разговор.

Поддерживаются два контура:

#### Native Omni

- двусторонний поток аудио;
- server/client VAD в зависимости от провайдера;
- частичные транскрипты;
- audio delta от модели;
- barge-in: речь пользователя немедленно останавливает воспроизведение и отменяет текущую генерацию;
- текстовая копия реплик сохраняется как обычные messages/turns.

#### Modular Voice

- захват микрофона;
- VAD и нормализация аудио;
- streaming/batch STT;
- обычный turn через Model Gateway;
- потоковый TTS по предложениям;
- отмена turn и аудио при перебивании.

Локальные реализации подключаются адаптерами, например Whisper-compatible STT и Piper/Kokoro-compatible TTS. Конкретные модели не зашиваются в доменную логику.

Транспорт первой версии — один WebSocket на voice session с бинарными audio frames и JSON control/events. HTTP остаётся для создания сессии, настроек и загрузки файлов. В браузере захват выполняется через Web Audio API; Tauri использует тот же интерфейс с возможностью добавить native capture позднее.

По умолчанию сохраняются транскрипт и метрики, но не исходная запись микрофона. Хранение аудио включается отдельной настройкой.

### 3.3 Vision Runtime

Существующий Stage 6 остаётся фундаментом: image attachments неизменяемо привязаны к turn, возможности модели обнаруживаются через gateway, OCR является отдельным fallback-инструментом.

Расширение добавляет:

- несколько изображений в одном turn;
- вставку из буфера, камеру и снимок экрана;
- live vision как контролируемую выборку кадров, а не бесконечную отправку видео;
- ручной выбор `Vision model`, `OCR` или `Auto`;
- предварительный просмотр перед отправкой;
- явный индикатор, какие кадры реально попали в контекст;
- лимиты разрешения, количества кадров и токенов;
- повтор turn с тем же неизменяемым набором вложений.

Live vision использует отдельный frame sampler. Он отправляет кадр при заметном изменении сцены, явной команде пользователя или с заданным безопасным интервалом. Это снижает расход VRAM и API-токенов.

### 3.4 Media Runtime и ComfyUI

Media Runtime выполняет долгие фоновые задания вне chat turn worker. Основной адаптер ComfyUI работает в двух режимах:

- встроенный управляемый сервис, запускаемый вместе с FinCtrl;
- подключение к существующему локальному или удалённому ComfyUI по URL.

Интерфейс содержит два уровня:

#### Быстрая генерация

Пользователь выбирает шаблон, вводит prompt/negative prompt, размер, seed, длительность и основные параметры. FinCtrl заполняет параметризованный workflow и ставит его в очередь.

#### Workflow Studio

Полноценный нодовый интерфейс открывается вкладкой внутри FinCtrl. Для максимальной совместимости с custom nodes первая версия встраивает официальный web-интерфейс ComfyUI через контролируемый same-origin proxy. FinCtrl добавляет сверху собственные вкладки, статус подключения, импорт/экспорт workflow, запуск, историю и переход к результатам. Это надёжнее самописного клона графа, который неизбежно отставал бы от экосистемы ComfyUI.

Workflow JSON хранится вместе с версией, входными параметрами и provenance. Результат можно повторить, скопировать параметры, открыть в Studio или прикрепить к чату.

### 3.5 Очередь и управление ресурсами

Генерация видео не должна ухудшать голосовой диалог. Resource Coordinator вводит приоритеты:

1. realtime voice;
2. активный текстовый/vision turn;
3. TTS/STT вне realtime;
4. image generation;
5. video generation.

Для одной GPU задаются профили `Conservative`, `Balanced`, `Maximum`. Координатор может приостановить новые media jobs, выгрузить локальную модель при поддержке runtime или предупредить о недостатке VRAM. Уже выполняющееся задание не уничтожается без явной отмены.

Очередь поддерживает `queued`, `preparing`, `running`, `paused`, `completed`, `failed`, `cancelled`, прогресс, повтор и восстановление после перезапуска.

### 3.6 Медиа-хранилище

Файлы хранятся отдельно от SQLite в управляемом каталоге, а база содержит метаданные:

- MIME, размер, checksum и dimensions/duration;
- источник и provider/model;
- workflow, seed и параметры;
- session/turn/job linkage;
- thumbnail/poster;
- даты создания и удаления.

Удаление использует корзину и последующую очистку. Дедупликация выполняется по checksum. Пользователь может отключить сохранение промежуточных ComfyUI-результатов.

### 3.7 События и восстановление

Новые подсистемы используют существующий event store. Ключевые события:

- `voice.session_started`, `voice.state_changed`, `voice.transcript_delta`;
- `voice.user_committed`, `voice.audio_delta`, `voice.interrupted`;
- `vision.frame_selected`, `vision.frame_attached`;
- `media.job_queued`, `media.job_progress`, `media.output_created`;
- `media.job_failed`, `media.job_cancelled`.

Частые audio chunks и video preview frames не записываются по одному событию в SQLite. Сохраняются смысловые checkpoint-события и агрегированные метрики. После обновления страницы UI восстанавливает transcript, turn, media queue и готовые outputs, но не пытается воспроизвести уже прозвучавшее аудио.

Каждое событие содержит session/job scope. Backend запрещает запрос, отмену или подписку на media/voice-объект другого чата без явной глобальной галереи. Это сохраняет строгую изоляцию контекста.

## 4. Пользовательский интерфейс

В основном чате появляются только компактные элементы:

- кнопка микрофона;
- индикатор состояния голоса;
- кнопки камеры/экрана рядом с вложениями;
- кнопка «Создать медиа»;
- компактная карточка текущей генерации.

Все провайдеры, устройства, VAD, голоса, качество, VRAM-профиль и ComfyUI URL находятся в Settings, а не в шапке чата.

Новые разделы Settings:

- `Voice`: микрофон, динамик, режим Auto/Omni/Modular, STT, TTS, голос, VAD;
- `Vision`: модель, OCR fallback, лимиты кадров и камера;
- `Generation`: ComfyUI, каталог моделей, очередь, preview и хранение;
- `Providers`: локальные/API-профили и проверка соединения;
- `Performance`: GPU-профиль и лимиты параллелизма.

Справа открывается Media Workspace с вкладками `Generate`, `Workflow`, `Queue`, `Gallery`. Панель скрываемая и изменяемая по ширине. На узком экране она становится полноэкранной внутренней страницей, а не отдельным окном ОС.

## 5. Надёжность и безопасность

- микрофон, камера и screen capture требуют явного разрешения;
- активный захват всегда видим и останавливается одной кнопкой;
- удалённый ComfyUI считается недоверенным endpoint: URL валидируется, private-network policy настраивается явно;
- workflow и custom nodes не получают дополнительные права FinCtrl;
- API-ключи маскируются в логах и событиях;
- media downloads проверяются по размеру и MIME;
- cancellation идемпотентна;
- WebSocket имеет heartbeat, sequence numbers и resumable control channel;
- ошибка TTS не уничтожает готовый текстовый ответ;
- ошибка Vision не отправляет пустой или неверный turn без подтверждения;
- ошибка ComfyUI изолируется от чата.

## 6. Значения по умолчанию

- работа local-first;
- API-профили выключены до настройки;
- голосовой режим `Auto`: Omni при полной совместимости, иначе Modular;
- VAD включён, barge-in включён;
- аудиозаписи не сохраняются;
- live vision отправляет кадры только по событию/существенному изменению;
- media concurrency: одна GPU-задача;
- resource profile: `Balanced`;
- ComfyUI запускается отдельно и не обязателен для старта FinCtrl;
- встроенный Workflow Studio доступен только при успешной проверке ComfyUI.

## 7. Критерии завершения FinCtrl 3.0

1. Пользователь может провести голосовой диалог как через Omni, так и через STT/LLM/TTS.
2. Перебивание останавливает речь модели и отменяет связанную генерацию без зависшего состояния.
3. Транскрипт и turn восстанавливаются после обновления страницы.
4. Vision принимает файл, камеру и screen capture, показывая реально отправленные кадры.
5. Image/video workflow запускается из Quick Generate и Workflow Studio.
6. Очередь и прогресс восстанавливаются после перезапуска backend.
7. Результаты доступны в галерее и прикрепляются к конкретному чату без утечки в другие контексты.
8. Обычный текстовый чат работает без Voice, Vision, ComfyUI и document router.
9. Локальная конфигурация работает без API-ключей; каждый API-провайдер можно независимо включить и проверить.
10. Недоступность любого дополнительного runtime не мешает запуску основного приложения.
